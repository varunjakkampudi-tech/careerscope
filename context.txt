01. PRODUCT PURPOSE AND TERMINOLOGY
----------------------------------
CareerScope, formerly Job Radar, is a private, single-owner job-search workspace.
It combines resume parsing, editable candidate preferences, multi-source job
collection, explainable matching, lead management, and supervised application
preparation. A separate static website publishes a sanitized job snapshot.

Core goals:
- Find relevant jobs using evidence from a saved resume and explicit preferences.
- Explain why a job matches instead of presenting an unexplained percentage.
- Preserve full descriptions and verified employer links where available.
- Distinguish incomplete data, blocked sources, and unavailable integrations.
- Keep applications under the owner's control and private information private.

Terminology:
- Job: a normalized posting, independent of the owner's relationship to it.
- Lead: a job matched to a profile, with scores, status, and an optional note.
- Profile: candidate facts, job preferences, and application information.
- Search run: a persisted collection operation with progress and source results.
- Application run: a separate supervised preparation/submission attempt.
- Public snapshot: allowlisted posting metadata suitable for public browsing.
- Admin snapshot: encrypted, read-only matching data; not a live database view.

Importing or finding a job does not mean an application was submitted. A model
score is not an employer evaluation, a qualification certificate, or a guarantee.


02. APPLICATION SURFACES AND DEPLOYMENT BOUNDARIES
------------------------------------------------
A. Private full application
   React UI + Fastify API + SQLite + private filesystem storage.
   Supports profile editing, collection, matching, lead changes, exports, and
   optional application preparation. Normally protected by owner login.

B. Public jobs inside the React application
   /jobs is publicly accessible. It is distinct from the authenticated workspace.
   The root route redirects to /jobs; /workspace chooses onboarding or leads.

C. Standalone GitHub Pages site
   Built from mobile-site/, staged into _site/ with an explicit allowlist.
   Serves public jobs and an encrypted admin snapshot without a running API.
   Cannot run searches, mutate the private database, or execute Copilot.
   Public URL: https://varunjakkampudi-tech.github.io/careerscope/

D. Local Docker stack
   Separate API/UI container, SQLite data volume, optional private Ollama service.
   Publishes the app only on 127.0.0.1:5180. Does not mount the host owner's data.

E. Optional remote full-app deployment
   Existing infrastructure describes API + nginx + HTTPS/certificates and an
   opt-in browser/application runtime. Local Docker success does not establish
   that the server, TLS, browser worker, or EC2 configuration is production-ready.

F. Copilot shared-browser workflow
   The owner explicitly shares browser pages with an assistant and reviews a
   handoff request. It is separate from the app's isolated worker, Gmail OAuth,
   browser session, and persisted application timeline.

-------------------------------------------------

Architecture style: modular monolith, not microservices.

  Browser UI -- HTTP / SSE --> Fastify routes
                                  |
                         composed API services
                           /      |       \
                 repositories   matching   providers -- HTTPS --> job sources
                      |           |           |
                    SQLite        |       normalized job data
                      |           |
               private files     optional semantic client
                                    |               |
                                 Ollama          Anthropic

Ownership rules:
- Shared contracts belong to packages/shared and are validated at boundaries.
- Resume parsing derives candidate data; it does not own database persistence.
- Matching owns eligibility, score computation, and semantic-result validation.
- Providers adapt external responses into the common job representation.
- Providers use matching's demand extraction when preparing job data.
- API routes handle HTTP and delegate business behavior to services/repositories.
- container.ts constructs dependencies and selects optional capabilities.
- The React app depends on shared browser-safe contracts, not backend services.
- MCP tools reuse the domain implementation instead of duplicating search logic.
- Runtime configuration is parsed centrally; secrets do not become UI props.

V1 retains SQLite and persisted run state executed in one API process until
deliberate migration. V2 instead requires PostgreSQL and dedicated BullMQ workers,
including an isolated AI worker. Preserving v1 is not a recommendation to carry

07. END-TO-END SEARCH PIPELINE
-----------------------------
1. The authenticated UI or MCP tool supplies validated search settings.
2. The API checks the saved profile and source capabilities.
3. A queued search_runs record is persisted; HTTP search creation returns 202.
4. The queue executes one search run at a time with bounded provider concurrency.
5. Providers fetch external data under HTTP budgets, cancellation and rate limits.
6. Results are normalized: company/title/location, salary, source IDs, URLs,
   description completeness, tech requirements, dates and provenance.
7. Canonical identities/fingerprints remove duplicate postings across sources.
8. Deterministic matching applies exclusion rules and computes explainable scores.
9. Result caps/thresholds limit the shortlist before expensive enrichment.
10. Company enrichment adds verified websites, careers portals and email evidence.
11. Optional semantic reranking evaluates eligible full-description candidates.
12. Repositories persist jobs, companies, lead scores and run results while
    preserving task-relevant existing statuses, notes and stronger information.
13. Persisted run events feed SSE so the UI can update progressively.
14. Terminal state records completion, partial failure, cancellation or failure.

Events are persisted before delivery. SSE reconnects replay stored events and
merge live events without duplicating the replayed sequence. The fetch-based SSE
client can send authorization headers; secrets are never placed in query strings.

Partial provider failure does not imply the whole run found no jobs. Sources
report blocked, unavailable, incomplete or timed-out results explicitly. A startup
recovery process reconciles interrupted work; an interrupted run is not silently
treated as a completed one. Discovered ATS boards can inform subsequent searches.


08. MATCHING AND LOCAL AI
------------------------
The deterministic engine uses the candidate context and job requirements to
compute weighted dimensions. Skill demand is derived from the posting rather
than dividing matches by the candidate's entire resume vocabulary. Skill aliases,
recent experience, role/seniority and logistical preferences influence matching.
Weights/constants and exact gates are defined in packages/shared/src/constants.ts
and packages/matching/src/score.ts and its neighboring modules.

Current dimension weights (sum = 1.00):
  Skills         0.40     Role title    0.15     Seniority      0.12
  Experience     0.10     Location      0.10     Compensation   0.08
  Freshness      0.05
Default search window: 30 days. Default maximum results: 200. Search request
validation and caller settings may select other supported values.

Important invariants:
- Exclusions are gates; a semantic model must not override them.
- A snippet or unreadable description has low confidence and a score ceiling of
  0.80. A source claiming a full description is not sufficient without readable text.
- New searches default to 0.85; the private Leads view defaults to 0 so stored
  lower-scored leads can still be reviewed. Query and display filters differ.
- Unknown salary, location, dates or skills are not fabricated to improve scores.
- Heuristic scores remain recorded even when an optional LLM blend is applied.
- Semantic blending gives deterministic matching 60% and the model 40%, subject
  to confidence ceilings and exclusion rules.

Legacy semantic provider selection:
V1 retains optional hosted/local adapters for compatibility; their settings are
documented in the root .env.example and docs/RUNBOOK.md. They do not select the
v2 model or authorize hosted inference in v2. The required v2 policy above is
Ollama-only Qwen3.5 9B/4B through the isolated AI worker.

Legacy v1 adapter safeguards (not v2 runtime defaults):
- Only approved local HTTP origins; credential-bearing URLs/redirects are rejected.
- Structured JSON output, exact known posting IDs, numeric score range 0 through 1.
- Results are revalidated in code, not trusted just because a schema was requested.
- Request timeout: 120 seconds; response body cap: 262,144 bytes.
- UTF-8 byte budget plus reserve selects a 4K-16K context; oversized requests fail
  safely rather than relying on the server to silently truncate the input.
- Two inference threads, bounded generation, one posting per request, serial
  execution, at most five eligible leads for the local provider configuration.
- Cancellation, invalid replies, timeouts and unavailable models retain heuristic
  scores with warnings. No model tools or autonomous application actions are added.

Historical v1 CPU experiments are retained in docs/RUNBOOK.md, not as model
selection instructions here. They do not establish Qwen3.5 quality or performance.
Benchmark both v2 candidates on this host under the combined application workload;
record exact model digests, quantization, latency, memory/swap, JSON validity and
task quality. Linux Docker inference does not imply Apple Metal acceleration.

10. RESUME AND PROFILE LIFECYCLE
-------------------------------
Upload -> validate file -> store safely -> extract text -> derive fields ->
owner review/edit -> save profile -> build matching context -> search/rank.

Resume records contain metadata, a storage path, extracted text and derived data.
Original filenames are metadata, not trusted filesystem paths. Files use generated
identifiers. Parsing is evidence extraction, not authority to invent qualifications.
The saved resume is also the source for an approved application upload.
The current upload limit is 10 MiB; supported MIME types are PDF and DOCX.

Profile JSON can contain candidate, preferences and application details. Partial
imports merge supported fields; supplied arrays replace those arrays, omitted
fields remain unchanged, and imported resume IDs do not attach arbitrary files.
The owner should review imported/extracted values before saving or sharing them.

Examples of profile preferences include target titles, tech stack, locations,
remote policy, employment types, salary expectations, excluded companies and
keywords. Application information includes known contact/work facts and practical
details such as notice period. Actual profile values are intentionally not here.


11. DATA MODEL AND STORAGE
-------------------------
SQLite is used through node:sqlite, with migrations and repository-owned SQL.
WAL mode supports the existing persistence pattern. JSON columns retain structured
candidate details, match breakdowns, configuration and operation state where used.

Tables declared in apps/api/src/db/schema.ts:
- profiles: candidate/preferences/application data and resume association.
- resumes: stored-file metadata, extraction and derived fields.
- companies: verified employer metadata and provenance.
- jobs: canonical posting data, description, salary, URLs and unique fingerprint.
- search_runs: queued/running/terminal search state, settings and source results.
- run_events: ordered persisted events supporting logs and SSE replay.
- leads: profile-to-job relationship, scores/breakdown, status and notes.
- settings: persisted settings and schema/seed/scheduling-related state.
- application_runs: persisted supervised application attempt state.
- auth_owner: single-owner authentication record.
- auth_signing_key: signing material used by the session mechanism.
- auth_sessions: revocable session records.

Key relationships:
- A profile can reference an uploaded resume.
- A company can have multiple jobs.
- Leads link jobs to profiles; (profile_id, job_id) is unique.
- Canonical job fingerprints suppress duplicate postings.
- Run events are associated with a search run and ordered for replay.
- Application state and lead status are related but are not interchangeable.

Lead statuses: new, saved, applied, interviewing, rejected, dismissed.
Search statuses: queued, running, completed, failed, cancelled.
Typical search transition: queued -> running -> completed/failed/cancelled;
queued work can also be cancelled before execution. A partial source outcome is
recorded in diagnostics and is not a separate top-level search status.
Employment types: fulltime, parttime, contract, internship, temporary.
Seniority labels: intern, junior, mid, senior, staff, principal.

Runtime storage:
- DATA_DIR determines the active database, resumes and other private state.
- The host app and local Compose app intentionally use separate storage.
- Dedicated application-browser state can persist under the runtime data directory.
- Runtime directories, OAuth credentials, owner records, signing keys, resumes,
  browser cookies and private backups must never be committed or publicly staged.
- SQLite persistence is not the same as database encryption at rest.
- A database-only backup is not a complete backup of resumes or browser state.

14. APPLICATION PREPARATION AND APPROVAL BOUNDARIES
--------------------------------------------------
Two distinct workflows exist:

Shared browser handoff:
- The application panel generates a reviewable request containing lead identity
  and instructions, not private resume contents or secret values.
- Copying the request does not execute automation or start a worker run.
- An assistant uses only pages shared with the current chat and checks the exact
  job, employer route, prior attempts and permission before disclosing data.
- Source-first, source-only and verified-employer routes have different boundaries.
- This workflow does not automatically populate the isolated-worker timeline.

Isolated local Copilot worker:
- Requires ENABLE_APPLICATION_AGENT, a supported Copilot CLI setup/sign-in,
  an attached resume/profile, Playwright and a suitable display/runtime.
- Starts a separate SDK/CLI session and browser, not an existing chat/browser tab.
- Persists one application's progress at a time and exposes questions in the UI.
- Consent covers resume/form preparation, which can disclose information before
  final submission because employer sites may autosave.
- Unknown qualifications or answers are questions, never guesses.
- Approval responses use single-use IDs; stale responses are rejected.
- Review-first mode includes explicit review of actions and final submission.
- A per-job automatic-submission authorization option exists in the app, off by
  default; it does not authorize every account, terms, or uncertain action.
- Account creation, terms and sensitive choices retain explicit approval rules.
- Password entry, login and CAPTCHA are completed directly by the owner.
- Current assistant instructions can impose stricter approval requirements than
  an available application mode; a mode is not blanket external authorization.

Completion and uncertainty:
- A click, account-created email or redirect alone does not establish Applied.
- Confirmation must be new, visible and specific to the approved application.
- Confirmation heuristics are not independent employer receipts.
- Cancellation, disconnection or restart during submission may leave an unknown
  outcome. Do not automatically retry or switch portals in that state.
- Duplicate and uncertain-attempt guards require checking the employer portal.
- Acknowledgment is tied to the relevant attempt, not a reusable blanket override.

Optional Gmail verification uses a narrowly approved sender/recipient/destination,
recent unambiguous mail and direct code entry into an unchanged same-origin field.
It does not expose codes in events, follow arbitrary verification links, mark mail
read, or itself submit an application. The owner handles unsupported cases.

The local Ollama reranker does not replace this Copilot worker. A self-hosted
application agent and a general in-app assistant remain future work.


15. GMAIL AND SCHEDULING
-----------------------
Gmail collection currently requests gmail.readonly through Google OAuth.
Credentials are configured on the API host, not in a shared Gmail browser tab.
Configured status does not prove that the grant remains valid.

Alert ingestion:
- Recognizes supported LinkedIn/Naukri/Indeed HTML job cards and direct job URLs.
- Filters supported sender domains; this is not proof of sender authenticity.
- Scans a bounded recent-message set, currently at most 200 messages per run.
- Deduplicates canonical portal identities and sends extracted job-card content
  through normal normalization/matching.
- Does not store full messages or fetch attachments/tracking images.
- Does not follow opaque tracking redirects or support every message template.
- Mail arrival date selects alerts; it is not invented as the posting date.
- Snippet-only alerts stay capped at 0.80 until a separate verified import supplies
  a complete readable description.
- Does not send, delete, or mark messages read.

Automatic searches:
- Persisted UI settings take precedence over the initial environment interval.
- Settings can select daily scheduling, including a local time and IANA timezone.
- Saved source, date-window and threshold settings are reused.
- Scheduling avoids overlap and records attempts for UI diagnostics.
- A delayed host wake can allow a catch-up attempt, not replay every missed run.
- A queued attempt is not evidence that providers completed successfully.
- API process and host must remain running/awake. There is no guaranteed 24/7
  service merely because the scheduling setting or Docker restart policy is on.


16. PUBLIC PAGES AND ENCRYPTED ADMIN EXPORTS
------------------------------------------
Private SQLite leads
  -> public exporter -> allowlisted jobs.json
  -> admin exporter  -> encrypted admin.enc.json
  -> staging guard   -> _site/ allowlisted artifact
  -> authorized GitHub Actions publication -> static public/admin pages.

Public output contains sanitized posting metadata and links, not private notes,
candidate contact details, resume files, credentials or private matching statuses.
Admin output adds selected scores/statuses and minimal matching-profile metadata,
but still excludes private fields not required by that viewer.

The admin passphrase is distinct from the owner's password. Encryption happens
before publication; decryption happens in the viewer's browser. The publicly
downloadable ciphertext can be attacked offline, so a strong passphrase matters.
Changing a future export does not revoke older published ciphertext copies.

The viewer is read-only and works from the last exported data while the API is
offline. Decrypted data and any unlock-session material are sensitive; follow
the current session/lock behavior documented and tested in the crypto/admin code.
Never describe a static snapshot as a live authenticated backend session.

Relevant commands, only publish/export sensitive artifacts with current approval:
  npm run mobile:export
  npm run mobile:admin

17. AUTHENTICATION, SECURITY, AND PRIVACY
---------------------------------------
Owner authentication:
- Single-owner credentials are hashed; sessions use signed HttpOnly JWT cookies
  backed by revocable database sessions.
- Production login requires HTTPS. Cookie/origin/proxy settings must agree with
  the actual deployment; development HTTP settings are not server defaults.
- Initial setup is constrained to the API machine/loopback request boundary.
- A Docker host-port request arrives from the bridge and cannot bypass that
  guard; the setup-owner command runs inside the container's loopback boundary.
- Login rotation and logout invalidate the relevant persisted session.
- A legacy API-key mode exists; keys are credentials with broad access and must
  not be exposed in URLs, client bundles, snapshots or logs.

Request and external-content safety:
- Zod validates configuration and input contracts.
- Origin/CSRF checks, configured CORS, rate limits and security headers protect
  applicable HTTP surfaces; keep them enabled in tests and deployments.
- Trust proxies only when the real reverse proxy overwrites forwarding headers.
- Treat resume text, job descriptions, emails and model output as untrusted data.
- Keep HTML/URL/SSRF and private-network protections in their owning modules.
- Do not weaken authentication, browser restrictions or TLS to make checks pass.
- Collection failures must not leak provider URLs containing credentials.

Data handling:
- Keep .env, databases, resumes, browser state, logs with private content and
  session backups out of Git, public artifacts and context exports.
- Avoid recording passwords, tokens, OTPs, full mailbox bodies or tracking URLs.
- Hosted model/application integrations can send approved profile/page data to
  their providers. Local inference keeps inference requests within its configured
  endpoint but does not make the entire application network-free.
- Local database storage is not encryption at rest; secure the machine and backups.
- Owner setup, recovery, deployment, account creation and application submission
  must retain their distinct authorization and operational procedures.

20. RELIABILITY, PERFORMANCE, AND RECOVERY
-----------------------------------------
Implemented mechanisms:
- Durable search/application state and database-backed event replay.
- One active search worker and bounded provider concurrency.
- HTTP timeouts, cancellation, safe retries/caching in provider abstractions.
- Per-source budgets and explicit partial outcomes.
- Deterministic fallback when optional model inference fails.
- Graceful shutdown/recovery behavior and health/readiness endpoints.
- Readiness checks include database availability and queue state.
- Session revocation and persisted state across ordinary API restarts.
- Isolated container acceptance for database backup restoration and auth behavior.

Operational caveats:
- Process health is not proof that external providers, OAuth or model inference work.
- A live model process is not proof of accurate or fast ranking.
- Search scheduling depends on process lifetime; no remote always-on service is
  implied by local configuration.
- A single-process queue is not a distributed-worker coordination mechanism.
- Resource limits are caps, not proof that a small server has sufficient headroom.
- The local VM must also fit OS/container overhead and any build/browser workloads.
- Full backup planning must include the database and relevant filesystem data,
  access control/encryption, retention, an off-host copy and a verified restore.
- Never run destructive tests or recovery commands against the owner's data.
- Application submission uncertainty is handled conservatively, not retried blind.

Server acceptance still requires real-host TLS/proxy checks, resource/load tests,
backup/disaster recovery, restart/rollback rehearsal and browser-runtime evidence.

22. CURRENT LIMITATIONS AND FUTURE WORK
--------------------------------------
Implemented but optional or constrained:
- Gmail read-only ingestion, not mailbox mutation.
- Local semantic ranking, not an autonomous local application agent.
- Copilot preparation, dependent on its CLI/runtime/consent and supported portals.
- Static public/admin views, not a remotely hosted private backend.
- Local container foundation, not validated AWS production deployment.

Requested v2 direction that remains unfinished:
- Durable Gmail processing checkpoints with mark-read only after verified import
  completion, explicit expanded OAuth consent and safe partial-failure handling.
- A self-hosted application-preparation agent preserving account, submission,
  duplicate and uncertain-outcome approval controls.
- An in-app assistant with bounded capabilities and no arbitrary shell/database
  execution or implicit permission to disclose candidate data.
- Representative model quality/latency tests, prompt-injection evaluation and
  hardware/runtime selection within the actual hosting budget.
- Verified 24/7 operation on a chosen server, with TLS, backups, restore, logs,
  resource limits, browser isolation, rollout and rollback procedures.

Other limits:
- Multi-user tenancy is not implemented just because some schema fields could
  accommodate future ownership changes.
- No universal ATS coverage, CAPTCHA bypass or guaranteed complete job inventory.
- No guarantee a listed job remains open or that a high score gets an interview.
- No email/push progress notification feature is implied by in-app events.
- Accessibility and browser checks do not cover every physical device or reader.
- CPU inference and paid/cloud hosting constraints cannot be solved by adding
  caches or by describing the app as free or 100% production-ready.

## ARCHITECTURE

No architecture change. One CI step was split into three so a failure names
itself; the three checks had been chained with && behind a single step name,
which is why every log said only "Process completed with exit code 1".

## UX

The defect was a real mobile UX defect, not a test problem. At 390px in WebKit
the lead rows physically overlapped each other by 28px.

## IMPLEMENTATION

Root cause, in apps/web/src/components/LeadTable.tsx:

Crossing the card/table breakpoint calls virtualizer.measure() to clear stale
heights. WebKit delivers ResizeObserver entries BEFORE React layout effects, so
the sequence there is: rows measured -> measure() discards those heights ->
nothing resizes again -> the size cache is never refilled. Every row then keeps
the 233px CARD_ESTIMATE while rendering 261px tall. Chromium and Firefox
deliver after the layout effect and were unaffected.

Fix: after clearing the cache, re-measure the mounted rows directly.

Also removed an arbitrary `timeout: 5000` on the one wait in check-ui.mjs that
had it - every other wait in that file uses the 30s default - and separated
"data has loaded" from "layout has settled", so the two are no longer conflated.
On failure the check now reports actual row geometry.

Iteration:  4
Phase:      implementation -> validation

## REQUEST

A visible way to understand what the AI engineering team is doing: live agent
state, models, permissions, progress, findings, activity and completion - read
from real repository state, with no simulated activity and no fake percentages.

## RECON

Established what could honestly be delivered before building anything:

  - VS Code does NOT publish agent runtime to disk. No script can observe which
    agent is executing, its elapsed time or its current tool. Anything claiming
    to would be fabricating.
  - Models are not pinned; the picker decides at run time.
  - The review tables in .ai/ are currently empty, so findings are genuinely
    zero rather than unknown.

Those three facts shaped the design rather than being worked around.

## ARCHITECTURE

A single dependency-free Node script reading files. No frontend application, no
server, no framework. It reads .ai/ and review.txt and nothing else, so the
application cannot depend on it and cannot be affected by it.

The load-bearing design decision is STALENESS. Because "active agent" is a
record written by the Orchestrator rather than a probe of a live process, a
recorded RUNNING state that has not been updated for 15 minutes is displayed as
STALE instead of animated. A spinner over an abandoned run is exactly the fake
activity the request prohibits, and without this it would have been the default
behaviour.

Agent permission is derived from each agent's actual tool list, not from a
label, so READ ONLY / WRITE cannot drift from the enforced configuration.

## UX

Terminal rendering with a --watch mode and a VS Code task. Deliberately not a
web dashboard: a second frontend to display the state of the first frontend is
not the simplest maintainable implementation.

## IMPLEMENTATION

  - scripts/control-center.mjs, rendering: task, phase, iteration, status,
    active agent, model, permission, elapsed, operation, state age, all 11
    agent states, the progress matrix with per-area deltas against the previous
    commit, P0-P3 findings with origin and file, activity log, last review
    entry, next action, and a completion gate that states why it is not met.
  - .ai/LOOP-STATE.json extended with activeAgent, model, currentOperation,
    startedAt, updatedAt, a per-agent state map and an activity array.
  - Orchestrator given an explicit execution graph: parallel only for read-only
    agents, never two builders at once, plus the duty to keep LOOP-STATE current.
  - Two VS Code tasks: watching and one-shot.
  - Three new assertions in check-agents.mjs.

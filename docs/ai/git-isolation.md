# Git Isolation

The [baseline](baseline.json) records one existing worktree and a dirty shared
tree. The operator reports Git worktree support; Agent Sessions/worktrees UI
activation remains unverified. No branch or worktree was created for this task.
Do not substitute a supplied Mac path for the actual Windows workspace.

## Shared-Tree Fallback

Use approved literal disjoint [claims](ownership.md), retain pre-existing edits
and serialize shared-file integration. Parent alone owns state, package and
review records in this assignment. Documentation and runtime builders must not
stage, reset, stash, restore or overwrite each other's files. No Git operation
is authorized by this documentation assignment.

QA uses synthetic isolated resources; a separate worktree would not isolate a
shared database, ports, output directory or external service. Freeze the reviewed
input. A digest change during a check requires attribution and an affected rerun,
not an assumption that the other builder's edit is harmless.

## When Worktrees Are Approved

An operator may choose a separate worktree/session only under an explicit task
contract. Record base revision, branch/worktree identity, claims, dependencies
and integration owner without copying private configuration. Do not auto-create,
delete or blind-merge branches. Review each returned change, integrate one at a
time, inspect conflicts semantically and rerun checks on the integrated content.

Git isolation does not grant push, tag, release or production permission.
[Project state](../PROJECT-STATE.md) identifies `main` as the integration/deploy
branch for both stacks; a push is a deployment candidate. R5 approval and live
evidence are separate from a completed engineering task. See [risk](risk-model.md).
